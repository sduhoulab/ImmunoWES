# ImmunoWES: Step-by-Step WES Analysis of a Matched Tumor–Normal Pair (YSU_T9/YSU_N9)

## Overview

**ImmunoWES** is a computational workflow for analyzing paired tumor–normal whole-exome sequencing (WES) data and deriving immunogenomic features. Its components cover sequencing quality control, read alignment, somatic variant calling and annotation, HLA typing, HLA evolutionary divergence (HED) estimation, and computational prediction of mutation-derived HLA-binding peptides. The full pipeline contains additional class I and downstream analysis modules; this tutorial demonstrates a defined subset using one matched pair.

This guide uses the normal gastric tissue **YSU_N9** and matched primary tumor **YSU_T9** from the publicly available gastric cancer dataset **SRP043661**. These are specimen identifiers from the original study; the example does not represent nine patients. It explains the inputs, dependencies, configuration, commands, and expected files so that readers can follow the computational steps without consulting the research article.

**Pipeline source:** https://github.com/sduhoulab/ImmunoWES

The following example uses `run_sample9.py` (the example command-line adapter) and `sample9.json` (its configuration file). The expected output paths below follow that adapter. Numerical results can vary with software and reference-resource versions; **expected filenames should not be mistaken for independently verified numerical results**.

```bash
mkdir -p tutorial_sample9_work/raw
fasterq-dump SRR1501968 --split-files -O tutorial_sample9_work/raw
```

Note: FASTQ files generated by SRA Toolkit need not have the same compressed-file MD5 checksums as the ENA-hosted `.fastq.gz` files. If using the accompanying `run_sample9.py` audit, obtain the **ENA original compressed FASTQs** whose MD5 hashes are encoded in the adapter, or adjust the audit to validate SRA-generated reads appropriately. The audit is designed to fail if the input is not consistent with its expected files.

## 2. Software and reference resources

The ImmunoWES workflow uses FastQC v0.12.1, MultiQC v1.19, BWA-MEM v0.7.17, SAMtools v1.9, Picard v2.18.23, GATK v4.0.4.0, ANNOVAR, HLA-HD v1.7.0, MHCflurry, MixMHC2pred, and R packages including maftools. This example also requires Python (3.11 or later), Bash, Perl, Java, and related command-line tools.

Required external reference resources include a GRCh38/hg38 FASTA and BWA index; dbSNP and Mills known-sites VCFs with indexes; `hg38.exon.bed`; ANNOVAR hg38 annotation databases (`refGene`, `avsnp144`, `gnomad41_genome`, and `dbnsfp42c`); HLA allele/reference files; aligned HLA protein sequences and the Grantham distance matrix; UniProt human protein FASTA; and MixMHC2pred weights/models. These are external dependencies and should be installed or obtained from their respective distributors, subject to licensing conditions.

**Software and database version consistency matters.** Record the versions and resource paths actually used. For this particular example, the configuration below specifies **dbSNP146** for BQSR. If a different resource release is used, record it when comparing outputs.

**Code layout.** The source scripts are maintained in the ImmunoWES GitHub repository. The accompanying `run_sample9.py` was written for a `gastric_cancer/` source-tree layout and accepts an `archive` path containing that layout. When using the repository checkout directly, ensure that the adapter points to the corresponding source files. The `prepare` command is only applicable to an archive-based setup; simply cloning a repository does not produce that archive automatically. This distinction concerns the location of input scripts, not the underlying analysis algorithm.

## 4. Running the example

First make the source scripts and reference databases available and edit `sample9.json` to match their local locations. Run all commands from the directory containing `sample9.json` and `run_sample9.py`. For an archive-based setup, first run `prepare`; otherwise use an adapter configured for the repository's actual directory layout.

Before analysis, inspect installed tools and verify the four FASTQ inputs:

```bash
python run_sample9.py sample9.json preflight
python run_sample9.py sample9.json audit
```

After the input audit succeeds, run the analysis stages:

```bash
python run_sample9.py sample9.json wes
python run_sample9.py sample9.json annotate
python run_sample9.py sample9.json hla
python run_sample9.py sample9.json hed
python run_sample9.py sample9.json peptides
python run_sample9.py sample9.json predict
```

For an archive-based setup, the preparatory command is:

```bash
python run_sample9.py sample9.json prepare
```

Run it **before** `preflight` and `audit`. Skip it when using a version configured to read scripts directly from the repository. The `predict` stage additionally requires a reviewed predictor-compatible HLA allele file in `reviewed_hla`; the value is intentionally empty in the example until those alleles have been checked.

`preflight` lists resource/software availability; it is not an end-to-end execution test. `audit` checks the four FASTQ inputs against the original sample-9 metadata and raises an error on inconsistent or missing files. Later stages require the preceding inputs and outputs. A successful audit should list the four expected FASTQ files with `OK` status. Check the per-stage logs and the files in Section 5 after each command; the commands alone do not establish that an analysis has completed successfully.

## 5. Expected outputs

These are the files and directories produced when the corresponding command completes successfully:

| Stage | Expected output or log | Purpose |
|---|---|---|
| `preflight` | `tutorial_sample9_work/evidence/tools.tsv` | Resolved software executables and missing dependencies |
| `audit` | `tutorial_sample9_work/evidence/input_audit.tsv` | FASTQ file audit and MD5/check results |
| `wes` | `results/raw_qc/`, `results/clean/`, `results/bam/YSU_T9_bqsr.bam`, `results/bam/YSU_N9_bqsr.bam`, `results/vcf/YSU_T9_filter.vcf` | QC, processed reads, aligned BAMs and filtered VCF |
| `annotate` | `results/annotation/YSU_T9.hg38_multianno.vcf`, `YSU_T9.hg38_multianno.txt` | Variant annotation |
| `hla` | `results/hla_comparison.tsv`, `results/hla/all_normal_HLA.txt` | HLA calls organized from existing reports |
| `hed` | `results/hed_status.tsv` and locus-specific HED files | HED calculation status and values when available |
| `peptides` | `results/15mer/YSU_T9_filtered_filtered.txt` | Mutation-derived 15-mer candidates |
| `predict` | `results/YSU_T9_prediction.txt`, `results/rank_best_counts.tsv` | HLA-II prediction scores and a summary count |

All paths under `results/` above are relative to the configured `work` directory. Check that the relevant files exist and are nonempty, and inspect the run log for errors. The scripts write stage-specific log files under `tutorial_sample9_work/logs/`.

## 6. Interpretation and scope

This example demonstrates processing a matched tumor–normal pair and generating specified intermediate files and HLA-associated computational outputs. The `hla` step can organize previously generated HLA-HD allele calls; it does **not** independently compare HLA typing tools or validate allele-level accuracy. The supplied adapter covers a **class II** peptide prediction branch, but does not demonstrate the full class I, TMB, pathway-enrichment, or survival-analysis modules. Predicted HLA binding or presentation is not equivalent to experimental validation of T-cell immunogenicity.

The tutorial describes the expected workflow and files. A reader should assess successful execution from the command exit status, generated logs, and output artifacts rather than assuming success from this document alone.

For the complete ImmunoWES implementation and available modules, see https://github.com/sduhoulab/ImmunoWES.
